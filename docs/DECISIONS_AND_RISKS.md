# Decisions and Risks

Owner: product-architect. Rule: the official Participant Guide v2.1 is authoritative; the official starter repository
(`lifix-prog/Loopverse-AI_ML_Virtual_Module` @ `d598411`, 2026-10-08) requirements are satisfied
additionally wherever they don't contradict the PDF. Nothing is silently reconciled — every conflict or gap is below.
"ASSUMPTION" = our interpretation where neither source is explicit.

## 1. Discrepancies and decisions

| ID | PDF says | Starter says | Decision | Risk |
|---|---|---|---|---|
| D1 | Guide is **Version 2.1** (p1, footer p10). | `STARTER_README.md` names `ARES_Accord_24_Hour_Hackathon_Challenge_v2.2.pdf`; the repo actually contains `ARES_ACCORD_24_HOUR_VIRTUAL_CHALLENGE_LOOPVERSE_3.0.pdf` (= v2.1, MD5 `a06be603b97234321eaba5ff37c063c4`, byte-identical to our local PDF). | PDF v2.1 is authoritative. | A v2.2 may exist privately with different numbers; low (repo file is identical). |
| D2 | p10 gives a participant checklist; no point weights. | `judges_scoring_rubric.md` ("100-point rubric") is referenced but **absent** from the starter repo. | Use the official guide's p10 checklist; no scoring weights are inferred. | Unknown weighting; may under-invest in a scored area (e.g. bonus items). |
| D3 | Resources = power/water/oxygen/robot/bandwidth; agents choose **fixed mode packages** (p4); free trimming forbidden. | `output_schema.json`: free-form `oxygen_units, water_liters, power_kwh, food_rations` (no robot/bandwidth; food is not a PDF resource). | Internal model follows the PDF. Export `final_allocation.json` = one schema-shaped record per agent: `round, agent_id, proposal{mode, power, water, oxygen, robot, bandwidth, justification, power_kwh, water_liters, oxygen_units (aliases), food_rations: null}, vote, risk_score, flag_human_review`. Extra fields allowed. | A strict schema checker could reject extra/null fields. Mitigated by keeping every schema key present. |
| D4 | Votes are **ACCEPT / REJECT** (p5, p6). | Schema example uses `"vote": "APPROVE"`. | ACCEPT/REJECT everywhere internally and in UI; the schema-shaped export maps ACCEPT->`"APPROVE"`, REJECT->`"REJECT"` and keeps `vote_pdf`. | Judges may expect one vocabulary; both are present in the export. |
| D5 | Practice events are **absolute** decreases ("Available Power decreases by 4", p8). | `event_injection_format.json` uses percent (`power_reduction_percent: 30`), `duration_hours`, `affected_systems`, `trigger_time`. | Parser accepts official JSON, absolute changes, percent changes, `<res>_set`, forbidden modes and free text. Percent reduction removes `ceil(pool*pct/100)` (conservative). `duration_hours` is recorded and the change applies to the whole replanning cycle (no time simulation). All interpretation notes shown in UI before applying (preview). | Unseen event wording may be misparsed -> judge sees notes and can edit/retry; ceil rounding may make a borderline event infeasible. |
| D6 | **Five** agents (Commander + 4 departments) + a **deterministic validator outside the LLM** (p2, p7). | Checklist: "minimum 4 agents", "Validator Agent rejecting proposals"; README: "Commander + 4 Departments + Validator". | 5 LLM-capable agents + a deterministic validator module, shown in the transcript as sender "Validator" (`source=validator`), explicitly **not** an LLM. | A judge reading "Validator Agent" literally might expect an LLM; README/diagram explain. |
| D7 | Export final plan + negotiation log as JSON or CSV; evidence = opening log, post-event log, final plan files (p7, p9). | Output files: `final_allocation.json`, `council_transcript.txt/.json`, `crisis_handling_log.txt`, `architecture_diagram.png`. | Export bundle produces `final_allocation.json`, `final_plan.json`, `council_transcript.json/.csv/.txt`, `crisis_handling_log.txt`. Mermaid source and `docs/architecture_diagram.png` are included. | Genuine opening and post-event exports must still be captured separately for submission. |
| D8 | Approval needs PASS + 4 ACCEPT; Commander cannot bypass (p2, p7). | Bonus: "Human approval if risk score > 20". Both valid baseline plans have risk 24, so it would always trigger. | Records carry `flag_human_review = risk > 20`; an **optional** Judge Controls toggle (off by default) makes a plan that already passed the gate wait in `AWAITING_COSIGN` until the judge co-signs (-> APPROVED) or vetoes (-> VETOED). Implemented 2026-10-10 and tested in `tests/test_orchestrator_core.py`. | Bonus points possibly lost; avoids a gate that would block every baseline approval. |
| D9 | Agents may be rule-based, LLM, optimization or mixed (p7 "Your choice"); safe fallback required. | RULES.md §5: "agents must genuinely negotiate based on LLM outputs and deterministic validator feedback". | LLM providers are the primary mode; the rule-based policy is an explicitly labelled fallback/demo mode (per-message source badge + `fallback_reason`). Demo video must use an LLM provider. | Free-tier quota exhaustion mid-demo pushes turns to fallback; visible badges keep it honest. |
| D10 | Crisis Override (risk 28, second Sacrifice) only "after an event" (p8). | — | Orchestrator allows override only in EVENT scenarios; validator accepts only policies (24,1) or (28,2). | None material. |
| D11 | "Two accepted compensation commitments from different agents" (p4, p6). | — | ASSUMPTION: "accepted" = accepted by the **beneficiary** department in the transcript (`COMMITMENT_ACCEPTED`); the Commander counts as a distinct agent; owner != beneficiary. | A judge may read "accepted" as council-accepted; our stricter reading still satisfies it. |
| D12 | Templates give the Commander "first priority next cycle" for both L3 and M3 (p6). | — | ASSUMPTION: two ACCEPTED commitments with the **same exclusive claim** for different beneficiaries -> Commitment backing FAIL. | Blocks L3+M3 override plans unless agents craft other valid returns. |
| D13 | F3 return: "Engineering commits 4 **future** Robot units" (p6). | — | ASSUMPTION: future pledges are not charged to the current pool; a future pledge from a department that is itself sacrificing -> **warning only**. | Judge could consider it unfair; it is visible as a warning. |
| D14 | Minimums: >= 3 rounds before first approval, >= 1 rejected/revised proposal, >= 1 Sacrifice refusal (p5). | — | >= 3 rounds is **enforced** by the approval gate. Revised/rejected proposal and refusal are **tracked and displayed** (protocol panel), not force-injected; agent stance (request Standard first; never accept Sacrifice in the round first asked) makes them happen naturally. | An LLM might accept too early -> stance in prompt + "never same round" sanitisation; QA checks protocol flags. |
| D15 | "Every candidate plan has a version number" (p10). | — | ASSUMPTION: plan versions are numbered **globally per session**, so post-event versions continue the sequence (e.g. v4 approved -> event -> v5...). | None. |
| D16 | New plan or justified INFEASIBLE "within three minutes of the event" (p8). | — | Configurable `ARES_SCENARIO_DEADLINE_S=170` (10 s margin). On expiry -> `TIMEOUT`, no approval, old plan stays STALE. | Slow free-tier LLMs may hit TIMEOUT; mitigate with faster model / rule-based fallback. |

## 2. Other design decisions

| ID | Decision | Rationale |
|---|---|---|
| X1 | Python 3.13 + Streamlit + SQLite + `requests` (no agent framework). | Smallest reliable stack; frameworks allowed but add risk (p7 "reliable small system"). |
| X2 | Optimizer enumerates all 81 combinations and diagnoses infeasibility; **never approves**. | p10: optimizer allowed if shown working with agents + validator. |
| X3 | One LLM call per agent turn with that agent's private profile/state/memory only. | p2: no single model writing five viewpoints. |
| X4 | No hosted demo; local run only. | $0 budget; p9 allows a local app with clear startup instructions. |
| X5 | Council rules are enforced on every agent turn (`ares/agents/sanitize.py`): Sacrifice cannot be accepted in the round it is first requested and needs >= 2 return offers from different agents. If a model tries anyway, the turn is recorded as a refusal/objection and the visible message says "[Council rule overrode ...]". | Makes the PDF p5 minimums (>= 1 Sacrifice refusal, >= 2 returns) robust for any model while keeping the override transparent; the model still chooses who sacrifices, what to offer and how to vote. |
| X6 | Soft LLM budget: agents get `time_budget_s` = hard deadline - 20 s; below 4 s a turn uses the labelled rule-based policy. | PDF p8 asks for a result within 3 minutes of an event; free-tier latency (e.g. Groq 8K TPM) could otherwise end every slow run in TIMEOUT. |
| X7 | Factual announcements (briefing, plan drafts, validation, conflicts, approval text) are composed by the orchestrator under the Commander's name with `source=system`; the Commander's LLM turn is its REQUEST (target, mode requests, offers, override). | Saves LLM quota for the decisions that matter and keeps numbers in announcements exact; the UI badges these as SYSTEM, not LLM. |
| X8 | Plan versions are drafted only from what departments declared (+ accepted commitments); the Commander's target is a request, not a plan. | Departments keep real autonomy: a plan changes only because agents changed their positions. |
